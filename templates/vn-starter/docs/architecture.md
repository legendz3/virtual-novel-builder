## Boundaries

React owns routing, authentication, menus, modal dialogs, dialogue/choice UI, story progression, learning state, relationships, and saving. Phaser owns only drawing, sprites, animation, and graphical input. A future graphical input callback should return a semantic action to the React controller; it must not mutate story/save state inside a scene.

The aliases `@/`, `@app/`, `@game/`, `@components/`, `@phaser/`, `@services/`, and `@content/` resolve identically in Vite, TypeScript, and Vitest. Keep public input/output types precise. Strict TypeScript and unchecked indexed access are enabled. Runtime persisted data is additionally validated because TypeScript cannot validate IndexedDB or network data.

## Save contract and lifecycle

`SaveProvider` supplies `load`, `save`, and `delete`; all implementations validate `GameSave`. `migrateSave(unknown)` is the single entry point for schema migration/validation. It validates version 1, then applies relationship reward reconciliation; malformed/future versions still fail before reconciliation. Add explicit sequential migrations here before changing persisted format. Story variables must be JSON-serializable even though runtime state accepts unknown values.

`LocalSaveProvider` uses IndexedDB database `dating-sim`, object store `saves`, and key `OWNER:SLOT`. The guest owner is `guest`; authenticated owners are UUIDs. Default slot is zero. `close()` is available to callers managing provider lifetimes. Account-scoped storage prevents uploading another user's or a guest's progress during an auth transition. Auth changes remount the save scope; stale loads are ignored and stopped autosaves cannot mark another scope clean.

`SaveManager` coordinates:

1. Load local and optional cloud concurrently. Choose the newest valid payload timestamp, preferring local on ties. Cache a newer cloud save locally. A failed cloud read does not prevent using a valid local save. If no valid copy exists and a provider failed, stop hydration rather than overwrite unknown data with an empty save.
2. Start autosave only after loading. Every meaningful store action marks dirty. Debounce at 1500 ms; a separate 30-second interval saves during continuous activity. Hidden-document and pagehide handlers request best-effort persistence.
3. Serialize a snapshot, preserving `createdAt` and advancing `updatedAt`. Queue local writes in order. Only after the local transaction succeeds, enqueue an independent cloud UPSERT. A cloud stall cannot block the next local save.
4. Clear dirty state only if the snapshot is still current after the local write. Failure keeps dirty state for retry. Cloud failures are reported separately and never undo the local transaction.

Manual `saveGame`, `loadGame`, `hasSave`, and `deleteSave` are exposed through the manager. The React save context exposes readiness and local/cloud diagnostics. `waitForCloud()` supports deterministic integration tests; application save completion means local durability, not confirmed cloud durability.

### Deliberate limits

- Guest-to-account merging and transfer UI are deferred. A future explicit transfer can read the guest provider, save through the account manager, verify cloud success, and only then choose whether to remove the guest copy.
- Timestamps are client-generated; clock skew and simultaneous-device conflicts need a later product policy. No conflict UI or server revision protocol is implemented.
- Cloud errors retry on the next save; there is no background service worker or permanent network retry queue. A clean local snapshot is retained across reloads and can be manually re-synced.
- `deleteSave` deletes locally and attempts cloud deletion. A failed cloud deletion is visible in diagnostics; do not build a “delete everywhere” UI until deletion retry/tombstone behavior is defined, because a retained cloud copy can be loaded again.
- Pagehide/visibilitychange IndexedDB writes are best effort. Browsers may terminate before asynchronous work finishes. Regular autosaves are the primary protection. Browser storage can also be evicted or denied; local failure remains visible and does not mark progress clean.
- The current API targets one active tab. Multi-tab coordination is deferred; avoid claiming transactional cross-device/tab conflict resolution.
