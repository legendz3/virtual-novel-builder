# Reusable phone presentation

`StoryPresentation.phone` supplies a complete authored phone snapshot to [StoryPhone](../src/components/game/StoryPhone.tsx). React still owns story progression, choices, rewards and saves. The phone displays content and opens local attachments; it has no network, free typing, contact database, transcript ledger, audio lifecycle or story callbacks. Chapter One’s existing ArrivalPhone/arrivalProgress path is unchanged.

## Content contract

[PhonePresentation](../src/game/story/phone.types.ts) is a discriminated union validated by [phoneSchema](../src/content/phoneSchema.ts). Every snapshot has a unique `id`, registered `shellAssetId`, `owner` (`emma` or `sofia`), title and authored chrome. Chrome requires time, date label, battery percentage 0–100, charging, cellular/wifi/none network and airplane-mode values. These are story values, not live device readings.

| Mode          | Required content                                                                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wechat-chat` | `conversationId` and one or more messages. Each has unique ID, sender ID/name, incoming/outgoing direction, mandatory `showMeanings`, and rows or an attachment ID. |
| `document`    | Document ID, supported rows, mandatory `showMeanings`, and optional related attachment ID.                                                                          |

`PhoneRow` accepts either a Mandarin support row or `{ kind: "text", language: "en", text }` with nonblank English text. English rows render their text directly and require no fabricated pinyin/translation. Strict validation rejects mixed row shapes. Every Mandarin row has `hanzi`, tone-marked `pinyin` and natural English `meaning`; optional `showMeaning: false` can hide one row’s English. A containing message/document with `showMeanings: false` overrides any row-level true. Hidden meanings are omitted from DOM/accessibility rather than visually concealed. Chinese/pinyin remain visible. Authored titles, sender names, attachment descriptions and surrounding narration must also avoid answer cues before a reveal; schema validation alone cannot judge those semantics.

Attachments belong to the current snapshot. `plan-screenshot` has supported rows, a semantic description, optional original sender name and `defaultOpen`; it displays as an inline disclosure. `map` has a semantic description and optional neutral schematic (`marked-route`, `building` or `campus`). These diagrams are authored illustrations, not geographic navigation. References must resolve within the snapshot, message/attachment IDs must be unique and fields are strict. Include only the attachment definitions needed by that snapshot so unchosen private content cannot leak.

Snapshot identity controls local state. A new `id` resets open attachments; reopening the same view preserves its local state until the snapshot changes or unmounts. Map Back restores the triggering button’s focus and the phone scroll position. Disclosure toggling keeps focus on its button. Reload reconstructs content from the saved event, not an attachment/save ledger. Advancing/revealing the story requires the normal external story controls and a new authored presentation.

## Rendering and controls

[GamePage](../src/pages/GamePage.tsx) resolves the exact shell asset and mounts StoryPhone alongside ordinary narration/choices/Next. Keyboard events inside the phone region do not advance the story. [storyPhone.css](../src/styles/storyPhone.css) retains the physical 2:3 shell and measured aperture of the approved 1024×1536 PNG: left 205, top 85, right 820, bottom 1453; authored content begins below the notch. Chinese is at least 18px, pinyin/meaning 14px, and independent attachment controls 44px. Overflow scrolls inside the screen; story controls remain outside it.

[phoneScene.css](../src/styles/phoneScene.css) uses a 320–360px phone beside narrative on wide screens, stacking below 1000px. Natural stage height keeps the footer below reachable choices. The existing Phaser bitmap proportionally covers the whole phone stage, with intentional backdrop opacity 0.48; phone and controls remain opaque. This is a scoped presentation rule and does not change source art or earlier framing constants. Pause removes the phone-stage attribute and keeps only StoryPhone mounted, hidden and inert. Its current transcript offset and open attachment survive resume; pending movement is cancelled and consumed. Other scene UI retains its existing pause lifecycle.

## Optional orientation cues and manual reading

`scrollCue` is optional content metadata, not saved progress. `{ kind: "outgoing-message", messageId }` must identify the final outgoing chat message. `{ kind: "incoming-message", messageId }` likewise identifies the final incoming chat message. Both require the target direction to match; neither accepts a document target. `{ kind: "document-attachment", attachmentId }` must identify the document’s related map. Strict validation rejects mismatched modes, unresolved targets and extra tuning fields. Omission never causes automatic scrolling.

[usePhoneScroll](../src/components/game/usePhoneScroll.ts) waits for two consecutive positive-size animation frames. An incoming or outgoing message cue then waits 120ms and travels for 500ms; a document cue waits six seconds and travels for 650ms. Both use cubic ease-out. The target is measured when travel starts: fit its full content with 8px trailing room, or align an oversized target’s beginning 8px below the transcript top. The destination is clamped to the transcript range. An already visible target does not move. Overflow of at most 2px consumes the activation without movement or a control.

An overflowing view has a separate, minimum-44px **More below ↓** button below the physical shell, outside its aperture and story choices. Its accessible name is “Scroll down in phone.” The first explicit request can orient to the authored target; later requests move one transcript page with 32px overlap. At the bottom it becomes **Back to top ↑**, accessible as “Scroll to top of phone.” Explicit travel takes 350ms, keeps button focus and never changes the story or outer-page scroll. Native scrollbars, wheel/touch input and the labelled, focusable transcript remain available. An open map’s overflow control scrolls that detail view; Back remains a separate control.

Wheel, touch/pointer down, phone focus, navigation keys and any phone control activation cancel pending or active movement without undoing the reader’s offset. Hover does not cancel. A first cancellation consumes the automatic cue for that snapshot activation. Map opening cancels before remembering the main offset, starts detail at its top and focuses Back; Back restores the exact main offset and trigger focus without scrolling the outer page. Repeated presentations with the same snapshot ID preserve local state. A new ID or a fresh mount after leaving/reloading starts a new activation. No scroll offset, cue status or attachment state enters the save.

Pause, unmount and hidden-document transitions release timers and animation frames; pause/resume and visibility return never rearm the same activation. Resize/text expansion updates overflow and clamps the offset; resizing during travel cancels it, while a pending delay uses the updated target. Reduced motion keeps the reading delay but changes travel to an instant offset, including manual controls; enabling it during travel finishes the current valid target immediately. No automatic scroll changes focus or announces a live message.

These are four repeated event presentations across two of the nine snapshots. The [approved playtest-02 addendum](../production/chapter-06/revisions/playtest-02/director-scroll-addendum.md) specifies this behavior.
